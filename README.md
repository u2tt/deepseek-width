# 内容宽度调节（DeepSeek / Gemini）油猴脚本

一份脚本同时支持两个站点，装一次两站都能用：

- **chat.deepseek.com** —— 调节正文宽度（按相对比例），自动收起思考过程。
- **gemini.google.com** —— 调节整列内容（对话行、回答正文、输入框、免责声明）的宽度。

两边按域名分流到各自的实现，设置分开保存、面板互不影响。宽度都按**相对比例**算：最大值是当前窗口的内容区宽度，拖动浏览器窗口或折叠侧栏时宽度自动跟随，不需要重新拖滑块。设置面板不常驻页面，平时看不见，从油猴菜单点「⚙ 打开设置面板」调出，改完关掉。

## 安装

1. 浏览器装 Tampermonkey（或 Violentmonkey / 脚本猫）。
2. 装上 `content-width.user.js`（版本 3.0.0）：
   - 一键安装（推荐）：[Greasy Fork 安装页](https://greasyfork.org/zh-CN/scripts/603529) — 点页面上的「安装此脚本」，以后脚本有更新会自动升级；
   - 在线安装：打开本仓库里的 [content-width.user.js](content-width.user.js) 点 Raw，Tampermonkey 会弹出安装页；
   - 把文件直接拖进浏览器窗口，Tampermonkey 弹出安装页，点安装；
   - 或打开 Tampermonkey 面板 →「添加新脚本」，把文件全文粘贴进去，保存。
   - **以前分别装过 DeepSeek 版或 Gemini 版的，先删掉那两个旧脚本再装这一个**，避免两份脚本同时改同一页面。
3. 打开 https://chat.deepseek.com/ 或 https://gemini.google.com/ ，点浏览器工具栏的 Tampermonkey 图标，在菜单里点「⚙ 打开设置面板」，右下角弹出设置页。

已装过的版本更新后刷新页面即生效。

## 使用

两个站点的面板操作一致：

| 操作 | 效果 |
| --- | --- |
| 拖滑块 | 30% – 100% 无级调节，步长 1% |
| 面板上滚轮 | 微调 1%；按住 Shift 滚轮 10%；按住 Alt 滚轮 5% |
| 「满宽」/「90%」/ … | 快速跳到常用比例（DeepSeek：满宽 / 90 / 80 / 70 / 原生；Gemini：满宽 / 90 / 75 / 60 / 原生） |
| 「原生」 | 撤销宽度改动，回到站点原始版式 |
| 「自动收起思考过程」（仅 DeepSeek） | 开：思考块只留「已思考（用时 N 秒）」一行，点标题仍可展开；关：全部展开 |
| 「重新识别」「复制诊断」（仅 DeepSeek） | 页面改版后识别不到容器时手动重扫；复制识别结果用于反馈 |
| 拖面板标题 | 移动面板位置 |
| × / Esc | 关闭面板（设置已保存） |
| 油猴菜单「⚙ 打开设置面板」 | 唯一一条菜单项，调出设置页 |
| Alt+Shift+W | 打开 / 关闭设置页 |

设置立即生效并自动保存，下次进站沿用；两个站点各自记住自己的数值。

## 一、DeepSeek：宽度 + 自动收起思考过程

在 chat.deepseek.com 上做两件事：调节正文内容列的宽度；把回答前的思考过程收起到一行标题。

### 实现方式

- 不依赖 DeepSeek 的混淆类名，运行时按几何特征判定「居中定宽列」：实际宽度 ≥ 阈值、明显窄于父容器内容盒、在父内容盒里水平居中、且不是 `position:fixed/absolute` 或弹窗浮层。
- **不按 `max-width` 判定**。真实站点并不是用像素 `max-width` 定宽，而是 `width:752px; padding:0 220px` 这种「定宽 + 大左右内边距」实现居中列，看 `max-width` 会在真实页面上一个都匹配不到。
- 同一页会命中一串嵌套的居中块（消息列表、单条消息、段落），用文本量剔噪音：取文本量最大的候选，只保留文本量 ≥ 其 40% 的候选，外加宽度与它相差 ≤2px 的候选（保住无文字但等宽的输入区包裹层）。
- 被保留的最内层打 `data-dsw-col`（应用百分比）；其余被保留层、以及祖先里带像素 `max-width` 的层打 `data-dsw-uncap`，避免外层上限压住内层、避免百分比被层层相乘。
- 只用一条样式表规则覆盖，不动 DOM 结构：

  ```css
  html.dsw-on [data-dsw-col]{
    box-sizing:border-box; max-width:none;
    width:var(--dsw-pct,100%);
    padding-left:0; padding-right:0;
    margin-left:auto; margin-right:auto;
  }
  html.dsw-on [data-dsw-uncap]{max-width:none;}
  ```

  开关类挂在 `<html>` 上：`dsw-on` 控制宽度覆盖（关掉就完全回到原生宽度）。测量几何时临时摘掉 `dsw-on`，否则量到的是被覆盖后的宽度。思考块的收起不写 CSS —— 交给站点自己的折叠逻辑，脚本只负责点一下（见下）。

  百分比写在 `width` 上而不是 `max-width` 上，才能改掉站点那种 `width:752px` 的定宽；左右内边距清零，否则真实列 440px 的内边距会把内容挤没。
- 用百分比而不是像素，宽度天然随窗口变化，不需要在 resize 时重算，也没有一帧延迟。
- 面板放在 Shadow DOM 里，与站点全局样式互相隔离；面板文字与按钮不参与匹配（`#dsw-host` 整棵子树被排除）。面板默认 `display:none`，点菜单才创建并显示，关闭后只是隐藏，不占版面、不接管滚轮。
- **自动收起思考过程**：站点自己就有折叠功能 —— 点标题行，正文节点被 React 摘掉，整块从 1609px 缩到 34px，只剩「已思考（用时 N 秒）」加一个右向尖括号；再点一次又展开。所以脚本不去藏节点（CSS 藏会和站点自己的展开逻辑互相打架：它一展开，脚本又藏，来回闪），而是替用户点那一下。定位仍按「位置 + 文字」：取每条 `.ds-message` 的前两个子元素，文本以「已思考 / 思考中 / 正在思考 / 思考完成 / Thought for / Thinking」开头的那一层是思考块，块里的第一个子元素就是可点的标题行，打上 `data-dsw-think`（只作标记，不写样式）。判断是否已经收起不看类名，而是量块内除标题行外各子元素的高度之和，小于 4px 即算收起。还在输出的块（标题是「思考中 / 正在思考 / Thinking」）不碰，站点那时也不允许收起。点击前先冻结滚动锚点，点完按 0 / 60 / 180 / 420 / 900ms 加一帧 rAF 补位移 —— 收起会让下面内容整体上移。同一块 700ms 内不重复点、最多试 3 次（React 重渲染有延迟），第一下点标题行，没反应就点它的第一个子元素。用户自己点开过的块会被记下来，脚本不再替它收起；判据是 document 捕获阶段的 pointerdown，脚本自己的 `.click()` 不触发 pointerdown，所以不会误判。关开关时把这些块逐个点开恢复，并同样补位移。
- 状态用 `GM_setValue`；没有 `GM_*` 时回落到 `localStorage`。页面结构变化由 MutationObserver 触发重扫，另有 0.8s / 2.4s / 5s 三次兜底扫描与 resize 重扫。
- **容器缓存**：认准的容器记在内存里，结构没变就不重扫。老流程每次重扫都要先解除标记再重新识别，解除那一瞬间页面按原生宽度重排，拖动滑块时就是宽度一闪一闪；缓存之后重扫只重新打一遍标记，不再有这一下。切换会话（URL 变化）或容器被换掉时才真正重新识别，油猴菜单里也留了手动重识别。
- **多列同时标记**：一页里真正要跟着变宽的往往不止一层（消息列和底部输入区的包裹层是各自独立的两棵树）。按最内层候选逐个打标记，全部记进缓存；只记最后一个的话，清理陈旧标记时会把其余几个刚打上的标记当成旧的摘掉，结果是拖动滑块只有一部分区域变宽。
- **拖动时的帧合并**：滑块的 input 事件一帧内可能来好几次，每次改宽度都要重新折行 + 补偿滚动，叠在一起就是闪。所以第一次 input 时先冻结锚点，同一帧内的多次取值只保留最后一个，每帧最多应用一次；松手后再按 0 / 90 / 260 / 650ms 复查补偿，并把这次改动写进存储。按钮和菜单这类一次性改动仍走完整的多段补偿。
- **滚动锚定**：正文在可滚动容器里按常规文档流堆叠，宽度一变就重新折行，本体高度跟着变，同一段滚动位移指向的文字会整段换掉（虚拟列表项高还是异步重测的，改完还会再动一下）。改宽度前记下视口中心那一行元素及其祖先链的 y 坐标，改完立刻把 y 位移补回滚动位移，再在 90ms / 260ms / 650ms 复查三次。锚点用「冻结」的那一份：连续调节期间不重新取参照，否则每次都会抓到相邻的另一条消息，补完反而挪了一整条。锚点被虚拟列表换掉时，先用链上仍在文档中的最深层做参照，再不行就按这段文字的前 24 个字把同一行找回来量。
- **行级锚点**：视口正中那一点经常落在段与段之间的空隙里，命中它的会是一整条助手消息的正文容器（实测高度 50359px）。拿这种容器当参照等于没补 —— 它的上边缘被后续补偿钉住不动，而内部真正的这一段已经位移了。所以命中后要往下钻：逐层取「包含这一点、高度最小」的子元素，钻到不能再钻，得到高度只有几十像素的那一行（实测锚到一个 32px 高的标题）。候选里取「离视口中心最近」的那个，而不是「第一个命中的」。
- **窗口尺寸变化同样补偿**：除了拖滑块，拖浏览器窗口也会让正文重排，因此 resize 走同一条补偿路径。补偿必须**同步**做在 resize 回调里：resize 事件在浏览器排版之后、绘制之前派发，这时读一次位置再写 scrollTop，画出来的就是对齐后的样子；排进 setTimeout 会晚一帧，先画一遍错位的再跳回来，肉眼就是一跳一跳。之后按帧补到收敛（620ms 内每帧一次），再在 90 / 320 / 700 / 1300ms 复查四段。「用户自己在滚」用事件判据而不是位移判据。

### 已验证

模拟页（`test/mock-deepseek.html`：260px 侧栏、嵌套 1280/768 双层定宽列、768px 输入区、320px 干扰项、居中 660px 弹窗）无头 Chrome 实测：

- 1600×900 主区 1340px，滑块 100/85/60/40/30% → 列宽 1340 / 1139 / 804 / 536 / 402px。
- 1200×800 主区 940px，同样五档 → 940 / 799 / 564 / 376 / 282px。
- 把主容器强制改成 700 / 1000 / 500px，60% 下实测 420 / 600 / 300px。
- 「原生」后标记清零，列宽回到 768px；320px 干扰项与 660px 弹窗全程未被改动。

真实页面（分享页与登录后的对话页共用同一套消息虚拟列表组件）实测：

- 匹配到 1 个容器：`div.ds-virtual-list-items`，原生 `width:752px` + `padding:0 220px`。
- 窗口宽 1500：100% → 内容列 1500px，85% → 1275px，60% → 900px，55% → 825px。
- 窗口宽 1100：100% → 1100px，55% → 605px。同一个 55% 在两个窗口下得到 825 与 605，比例稳定。
- 登录后的对话页（1500×850，55%）实测内容列 825px，与分享页一致。

滚动锚定与窗口缩放补偿：

- 1500×850：100% → 55% → 80% → 100% → 40%，每一步视口中心那一行的纵向位移差都是 0px。
- 1100×700：同样四步，位移差 0px。
- 连续拖动（100% → 60%，每次 -2%、间隔 30ms，共 21 次）结束后，中心文字未变、位移差 0px。
- 窗口 1500 → 1000 → 1500 分 10 步拖动：脚本补的滚动位移 3000 → 3162（最窄处）→ 精确回到 3000，来回对称；锚点行上边缘 y 全程 411px 不变。可见区里其它行仍会随重新折行上下移动，实测最多 90px，这是改宽度必然带来的换行重排，不是补偿失效。

自动收起思考过程 + 设置面板（`test/mock-think.html`，页内脚本模拟站点自己的折叠逻辑）：

- 打开页面前面板不存在，两条「已思考（用时 N 秒）」块已收起：正文 `display:none`、块高 34px；标题为「思考中…」的流式块不动。
- Alt+Shift+W 打开后面板 `display:block`，开关为开，快捷按钮 5 个；关开关两块恢复 118px，再开回到 34px。
- 模拟用户点开某一块后等 700ms，它保持展开、另一块仍收起；× 与 Esc 都能关闭面板。

真实页面（1500×850，55% 档，内容列 825px）：

- 注入后 7 个思考块全部收起：块高 34px、只剩 3 个子元素、文本只剩「已思考（用时 N 秒）」，尖括号朝右，与站点自己点收起后的样子一致。
- 模拟用户点第一个块：块高 1609px、44 个子元素，2 秒后仍是展开状态，没被脚本重新收起。
- 面板开关关掉：7 个块全部展开；再开：除用户自己点开过的那一块外全部回到 34px。

## 二、Gemini：整列内容宽度

相同的思路搬到 gemini.google.com：整列内容（对话行、回答正文、输入框、免责声明、零态首页标题）按同一比例收窄并居中，回答里的段落、标题、列表也跟着列宽一起缩放。比例相对「内容区」算，拖浏览器窗口或折叠侧栏时自动跟随。

### 实现方式

- 侧栏 `bard-sidenav` 是 flex 兄弟项，`bard-sidenav-content` 的宽度天然等于「窗口 − 侧栏」。`chat-window` 的宽度写成 `calc(var(--gw-k) * 100%)`，`--gw-k` 是 0 到 1 的纯数字，比例因此始终相对内容区，侧栏一折叠或窗口变化都由浏览器自己重算。
- 不用容器查询 `cqw`：`chat-window` 在部分布局下拿不到容器宽度，`cqw` 与百分比一起退化成 `auto`，整列会塌成几十像素的窄缝，表现为用户气泡被推到最右边、回答区不收窄。
- `chat-window` 同时要 `flex:none`：它原生是 flex 子项，不取消拉伸时 `width` 会被 flex 布局覆盖，比例不生效。
- 通道打通：`.chat-container`、`.chat-history-scroll-container`、`infinite-scroller.chat-history`、`.conversation-container`、`user-query`、`model-response`、`model-response-disclaimers` 全部放开到 100%，列宽只由 `chat-window` 决定。
- 输入框 `.input-area-container` 原生 `position:absolute` 且宽 660px 上限，改成 `static` 后由 `input-container`（改为纵向居中）摆放，宽度跟随列宽；里面的输入框本体也放开上限，避免外层变宽、内部仍锁在 660。
- **回答正文的 708px 上限**：Gemini 给 markdown 里每个顶级块（段落、标题、列表、代码块）都写了 `max-width:708px; margin-inline:auto`，回答头部栏、脚注、操作按钮也是 708px 加一个 JS 算出来的 `margin-left`。列宽超过 708px 之后，正文不再变宽、只是整体挪位置 —— 这是「比例看起来在某个档位以上失效」的直接原因。脚本把这些块放开到 100%，把 708px 的 chrome 元素改成满宽无外边距。
- 只有 `--gw-k` 一个动态量，其余全是静态 CSS，窗口变化由浏览器自己重算。
- **面板 DOM 全部用 createElement 搭**：Gemini 开了 Trusted Types，`shadowRoot.innerHTML = '...'` 会直接抛 `This document requires 'TrustedHTML' assignment`，面板建不出来。
- 状态用 `GM_setValue`，没有 `GM_*` 时回落 `localStorage`；Gemini 是 SPA，样式表被框架换掉时脚本每 1.5 秒补回。

### 已验证

无头 Chrome，模拟页 `test/mock-gemini.html`（1400×1000 iframe，会话视图与零态首页两种）与真实页面 gemini.google.com/app：

| 场景 | 结果 |
| --- | --- |
| 模拟页 100% | 列 1112@288，等于内容区满宽 |

| 模拟页窗口收窄 | 宽 1112 → 窄 672，列 890 → 538 |
| 模拟页回滚 | 摘掉开关后输入框位置与原生完全一致 |
| 模拟页断言 | 会话视图 14 项、零态 13 项全部通过 |

| 真实页 85% | chat-window 1044@144、段落 1032@156、输入框 1012@160 |
| 真实页 70% | chat-window 860@236、段落 848@248、输入框 828@252 |
| 真实页 60% | chat-window 737@298、段落 725@310、输入框 705@314 |

已知限制：侧栏占位决定了内容区上限，所以 100% 就是「内容区满宽」，比 Gemini 原生版式（正文 708px 居中）宽得多，正文行会很长；想接近原生阅读宽度用 55% – 60%。

- `content-width.user.js` — 用户脚本本体，装这个（两站通用）。
